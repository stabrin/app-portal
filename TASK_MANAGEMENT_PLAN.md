# План разработки модуля "Управление задачами"

Этот документ описывает план разработки нового модуля "Управление задачами" в интерфейсе администратора.

## 1. Цели и задачи

- Создать функционал для генерации, управления и отслеживания производственных задач.
- Задачи создаются на основе "Заказов на производство" с определенными сценариями маркировки.
- Обеспечить гибкость настроек для разных типов задач.

## 2. Проектирование структуры базы данных

Предлагается создать новую таблицу `production_tasks` для хранения задач.

### Таблица `production_tasks`

| Поле | Тип | Описание |
|---|---|---|
| `id` | `SERIAL PRIMARY KEY` | Уникальный идентификатор задачи. |
| `order_id` | `INTEGER REFERENCES orders(id)` | Ссылка на заказ, из которого была создана задача. |
| `task_type` | `VARCHAR(50)` | Тип задачи ("manual_aggregation", "custom_algorithm"). |
| `status` | `VARCHAR(50)` | Текущий статус задачи ("new", "in_progress", "completed", "error"). |
| `settings_json` | `JSONB` | Настройки задачи в формате JSON. Структура зависит от `task_type`. |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | Дата и время создания задачи (по умолчанию `NOW()`). |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | Дата и время последнего обновления. |
| `assigned_to_user_id` | `INTEGER REFERENCES users(id)` | (Опционально) Ссылка на пользователя, которому назначена задача. |
| `result_data` | `JSONB` | (Опционально) Поле для хранения результатов выполнения задачи. |

### Структура `settings_json`

**Для `task_type = "manual_aggregation"`:**
- Детализация по GTIN, количество.
- Информация о том, какие данные сканировать.
- Пример:
    ```json
    {
      "aggregation_level": "box",
      "items_per_box": 10,
      "gtins": ["04601234567890", "04601234567891"]
    }
    ```

**Для `task_type = "custom_algorithm"`:**
- Имя или ID скрипта/алгоритма для выполнения.
- Параметры для алгоритма.
- Пример:
    ```json
    {
      "algorithm_name": "special_report_generator",
      "parameters": {
        "report_format": "pdf",
        "include_sscc": true
      }
    }
    ```
Такая структура позволит легко расширять функционал в будущем.

## 3. План реализации

### Шаг 1: Миграция базы данных
- Создать скрипт для добавления таблицы `production_tasks` в существующую базу данных клиента.

### Шаг 2: Бэкенд (Сервисный слой)
- **`OrderService`**: Добавить метод `create_task_from_order(order_id)`.
    - Метод будет проверять сценарий заказа.
    - Если сценарий подходит, он будет создавать запись в `production_tasks`, формируя соответствующий `settings_json`.
- **`TaskService`** (новый сервис): Создать новый сервис для работы с задачами.
    - `get_tasks()`: Получение списка всех задач.
    - `get_task(task_id)`: Получение деталей одной задачи.
    - `update_task_status(task_id, status)`: Обновление статуса задачи.
    - `update_task_settings(task_id, settings)`: Обновление настроек задачи.

### Шаг 3: Фронтенд (Интерфейс администратора `admin_ui_qt.py`)
- **использовать существующий пункт меню**: В левое меню использовать существующий пункт "Управление задачами".
- **Создать новую страницу**: Создать виджет для отображения списка задач, аналогично "Управлению заказами".
- **Таблица задач**: На странице разместить таблицу со списком задач (ID, ID Заказа, Тип, Статус, Дата создания).
- **Панель управления задачей**: При выборе задачи в таблице, справа должна появляться панель для просмотра/редактирования.
    - Отображение основных данных задачи.
    - Редактор для `settings_json` (возможно, в виде простого текстового поля для JSON на первом этапе).
    - Кнопки для управления задачей (например, "Взять в работу", "Завершить").
- **Интеграция с заказами**: В `on_order_select` в `AdminWindowQt` добавить логику для отображения кнопки "Создать задачу", если заказ подходит по условиям.

### Шаг 4: Тестирование
- Проверить создание задачи из заказа для обоих типов сценариев.
- Проверить отображение списка задач.
- Проверить обновление статуса и настроек задачи из интерфейса.
