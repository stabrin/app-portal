# План разработки модуля "Управление задачами"

Этот документ описывает план разработки нового модуля "Управление задачами" в интерфейсе администратора.

## 1. Цели и задачи

- Создать функционал для генерации, управления и отслеживания производственных задач.
- Задачи создаются на основе "Заказов на производство" с определенными сценариями маркировки.
- Обеспечить гибкость настроек для разных типов задач.

## 2. Проектирование структуры базы данных

Предлагается создать новую таблицу `production_tasks` для хранения задач.

### Таблица `production_tasks`

| Поле | Тип | Описание |
|---|---|---|
| `id` | `SERIAL PRIMARY KEY` | Уникальный идентификатор задачи. |
| `order_id` | `INTEGER REFERENCES orders(id)` | Ссылка на заказ, из которого была создана задача. |
| `task_type` | `VARCHAR(50)` | Тип задачи ("manual_aggregation", "custom_algorithm"). |
| `status` | `VARCHAR(50)` | Текущий статус задачи ("new", "in_progress", "completed", "error"). |
| `settings_json` | `JSONB` | Настройки задачи в формате JSON. Структура зависит от `task_type`. |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | Дата и время создания задачи (по умолчанию `NOW()`). |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | Дата и время последнего обновления. |
| `assigned_to_user_id` | `INTEGER REFERENCES users(id)` | (Опционально) Ссылка на пользователя, которому назначена задача. |
| `result_data` | `JSONB` | (Опционально) Поле для хранения результатов выполнения задачи. |

### Структура `settings_json`

**Для `task_type = "manual_aggregation"`:**
- Детализация по GTIN, количество.
- Информация о том, какие данные сканировать.
- Пример:
    ```json
    {
      "aggregation_level": "box",
      "items_per_box": 10,
      "gtins": ["04601234567890", "04601234567891"]
    }
    ```

**Для `task_type = "custom_algorithm"`:**
- Имя или ID скрипта/алгоритма для выполнения.
- Параметры для алгоритма.
- Пример:
    ```json
    {
      "algorithm_name": "special_report_generator",
      "parameters": {
        "report_format": "pdf",
        "include_sscc": true
      }
    }
    ```
Такая структура позволит легко расширять функционал в будущем.

## Фаза 2: Реализация логики выполнения заданий

На этом этапе мы реализуем основной функционал, связанный с непосредственным выполнением заданий операторами.

### 1. Проектирование и создание таблиц для выполнения заданий (Уточненная версия):
*   **Создать таблицу `task_employees`** для хранения сгенерированных кодов-пропусков для сотрудников.
    *   **Поля:** `id` (PK), `task_id` (FK на `production_tasks`), `access_code` (уникальный код), `employee_name` (опционально, для идентификации).
*   **Обновить/Создать таблицу `tasks_packages`** для поддержки многоуровневой агрегации (короб, паллета и т.д.). Эта таблица будет хранить иерархию вложенности и дополнительные данные для этикеток.
    *   **Поля:**
        *   `id` (PK)
        *   `sscc` (Код SSCC, уникальный)
        *   `task_id` (FK на `production_tasks`)
        *   `package_type` (Тип упаковки: 'блок', 'короб', 'паллета')
        *   `parent_package_id` (FK на `packages.id`, для вложенности. У паллеты родителем будет null, у короба - паллета).
        *   `quantity` (INT, nullable) - Количество единиц товара (для AI 37)
*   **Обновить/Создать таблицу `task_datamatrix_pool`** для управления жизненным циклом кодов и хранения динамических атрибутов.
    *   **Поля:**
        *   `id` (PK)
        *   `task_id` (FK)
        *   `gtin`
        *   `datamatrix`
        *   `status` (статус: 'available', 'reserved', 'printed', 'aggregated')
        *   `employee_id` (кто зарезервировал код)
        *   `package_id` (FK на `packages.id`, указывает на *непосредственную* упаковку, в которую вложен код, например, короб)
        *   `batch_number` (VARCHAR, nullable) - Номер партии (для AI 10)
        *   `production_date` (DATE, nullable) - Дата производства (для AI 11)
        *   `packaging_date` (DATE, nullable) - Дата упаковки (для AI 13)
        *   `best_before_date` (DATE, nullable) - Срок годности "Best Before" (для AI 15)
        *   `expiry_date` (DATE, nullable) - Срок годности/действия (для AI 17)
        *   `origin_country` (VARCHAR, nullable, для уточнения страны происхождения)
*   **Создать таблицу `task_control_codes`** для хранения управляющих штрихкодов.
    *   **Поля:**
        *   `id` (PK)
        *   `code` (VARCHAR, Уникальный) - Строковое значение управляющего штрихкода.
        *   `action` (VARCHAR, Уникальный) - Имя действия (например, 'CANCEL_LAST', 'CLOSE_PALLET', 'CLOSE_BOX', 'FINISH_TASK').
        *   `description` (TEXT) - Описание действия для пользователя.

### 2. Реализация генерации пропусков для сотрудников:
*   В редакторе задания (`TaskEditorFrameQt`) добавить кнопку "Сгенерировать пропуски".
*   При нажатии, на основе поля "Количество сотрудников", создавать записи в `task_employees` с уникальными `access_code`.
*   Реализовать интерфейс для просмотра и печати этих кодов-пропусков.
    *   **Требования к макету пропуска (этикетка 60x40 мм):**
        *   Номер контейнера (из связанного заказа).
        *   Название клиента (из связанного заказа).
        *   Текущая дата печати.
        *   Штрихкод, кодирующий `access_code`.
        *   Пустая область внизу для рукописных заметок.

### 3. Создание сервиса для наполнения пула кодов DataMatrix:
*   Создать фоновый процесс или сервисный метод, который при переводе задания в статус `in_progress` наполняет таблицу `task_datamatrix_pool`.
*   Сервис должен извлекать коды из `dmkod_aggregation_details.api_codes_json` или `items.datamatrix` в зависимости от `dm_source` в сценарии заказа.
*   Все извлеченные коды помещаются в `task_datamatrix_pool` со статусом `available`.

### 4. Разработка интерфейса оператора (исполнения задания):
*   *Этот пункт потребует отдельного, более детального планирования. Это будет новый UI, возможно, в отдельном окне или приложении.*
*   Создать новый UI, который открывается после сканирования кода-пропуска сотрудника.
*   В этом UI оператор сможет:
    *   Выбрать товар (GTIN) из задания.
    *   Запросить определенное количество кодов для печати.
    *   Запустить печать.
    *   Выполнить агрегацию (сканировать коды и SSCC).

### 5. Реализация бэкенд-логики для оператора:
*   Создать методы в `TaskService` для:
    *   **Обработка управляющих кодов:** При получении данных со сканера, система должна в первую очередь проверять, не является ли код управляющим (по таблице `task_control_codes`). Если да - выполнить соответствующее действие (отмена, закрытие упаковки) вместо обработки как данных.
    *   **Резервирования кодов:** атомарная операция, меняющая статус с 'available' на 'reserved' для заданного количества кодов и сотрудника.
    *   **Изменения статуса кодов** на 'printed' после печати.
    *   **Агрегации кодов:** создание/получение SSCC и проставление `sscc_id` у кодов со статусом 'printed', с последующим изменением статуса на 'aggregated'.

Часть 1: Разработка UI оператора (в desktop-app/src)
Шаг 1.1: Создание окна входа для оператора (operator_login_ui.py)

Цель: Создать модальное окно, которое будет принимать отсканированный код-пропуск сотрудника.
Компоненты:
OperatorLoginWindow(QDialog): Класс окна.
QLineEdit: Поле для ввода, которое будет постоянно в фокусе для приема данных со сканера.

Логика:

В случае невалидного пропуска, выводится сообщение об ошибке, и поле ввода очищается.

Часть 2: Реализация бэкенд-логики (в desktop-app/src/task_service.py)
Шаг 2.1: Добавление методов для аутентификации и получения данных

get_task_by_employee_pass(self, access_code):
Находит employee_id и task_id в таблице task_employees по access_code.
Если найдено, запрашивает данные о задаче/заказе и список уникальных gtin из task_datamatrix_pool для этого task_id.
Возвращает словарь с полной информацией для инициализации UI оператора.
Шаг 2.2: Реализация логики печати (Резервирование + Статус)

reserve_codes_for_printing(self, task_id, employee_id, gtin, quantity):
Атомарная операция: Использует SELECT ... FOR UPDATE, чтобы заблокировать строки.
Находит quantity кодов со статусом available и нужным gtin.
Если коды найдены, обновляет их статус на reserved, проставляет reserved_by_employee_id и reserved_at.
Возвращает список зарезервированных кодов. Если кодов недостаточно — возвращает ошибку.
mark_codes_as_printed(self, task_id, datamatrix_codes):
Принимает список кодов, которые были успешно отправлены на печать.
Обновляет их статус на printed в task_datamatrix_pool.
Шаг 2.3: Реализация основной логики сканирования

process_scan(self, task_id, employee_id, scanned_code):
1. Проверка на управляющий код:
Ищет scanned_code в task_control_codes. Если найден, выполняет действие (например, отмена последней агрегации) и возвращает результат.
2. Идентификация кода:
Если это не управляющий код, определяет его тип. Проверяет, есть ли он в task_datamatrix_pool (это DataMatrix задания) или соответствует формату SSCC.
3. Обработка DataMatrix:
Проверяет статус кода в task_datamatrix_pool. Он должен быть printed.
Если статус верный, код "привязывается" к текущей открытой упаковке сотрудника (потребуется временное хранилище или логика состояний).
4. Обработка SSCC:
Если отсканирован SSCC, все коды из текущей открытой упаковки получают этот sscc, и их статус меняется на aggregated. Упаковка "закрывается".
