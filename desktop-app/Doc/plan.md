# План: Расширение структуры БД для сопоставления кодов товаров (GTIN, EAN и др.) - Упрощенный подход

## 1. Проблема

Текущая таблица `public.products` хранит только российские GTIN. При работе с товаром оператор может сканировать альтернативный код (европейский EAN, код производителя), и системе необходимо найти соответствующий ему российский GTIN из справочника `public.products`.

## 2. Цель

Создать таблицу сопоставлений, которая будет связывать различные внешние коды (EAN, коды производителя) с существующими российскими GTIN в таблице `public.products`. Это позволит находить нужный товар по любому из его известных кодов.

## 3. Предлагаемая структура БД

Предлагается сохранить таблицу `public.products` без изменений и добавить одну новую таблицу.

### Таблица 1: `public.products` (Без изменений)

Эта таблица остается основным справочником товаров, где `gtin` является уникальным ключом.

-   **`gtin`** (VARCHAR, PRIMARY KEY): Уникальный российский GTIN.
-   **`name`** (VARCHAR): Наименование товара.
-   `...прочие поля...`

### Таблица 2 (Новая): `product_code_mappings` (Таблица сопоставлений кодов)

Это ключевая таблица, которая будет хранить все связи.

-   **`id`** (SERIAL, PRIMARY KEY): Уникальный ID записи сопоставления.
-   **`gtin`** (VARCHAR, FOREIGN KEY -> `public.products.gtin`): Ссылка на российский GTIN из основного справочника.
-   **`mapped_code`** (VARCHAR): Сопоставляемый код (EAN, код производителя и т.д.).
-   **`mapped_code_type`** (VARCHAR): Тип сопоставляемого кода. Рекомендуемые значения: 'EAN', 'MANUFACTURER_CODE'.
-   **`client_id`** (INTEGER, FOREIGN KEY -> `ap_clients.id`, NULLABLE): Ссылка на клиента. Если `NULL`, то сопоставление является глобальным.

**Ограничения:**
-   Создать уникальный индекс на `(mapped_code, mapped_code_type, client_id)` для предотвращения дубликатов.

## 4. План реализации

1.  **Создание новой таблицы:**
    -   В /home/tabrin/project/app-portal/desktop-app/scripts/setup_client_database.py добавить код для создания новой таблицы  `product_code_mappings` со всеми ключами и индексами.
2.  **Обновление интерфейса администратора:**
    -   Создать новый раздел в "Справочниках" под названием "Сопоставление кодов товаров".
    -   В этом разделе реализовать интерфейс для управления сопоставлениями: добавление, редактирование и удаление записей в `product_code_mappings`.
3.  **Адаптация логики поиска товара:**
    -   В тех местах, где происходит идентификация товара по сканированному коду (например, в окне оператора), необходимо изменить логику.
    -   **Новый алгоритм поиска:**
        1.  Попытаться найти сканированный код напрямую в `public.products.gtin`.
        2.  **Если не найден**, выполнить поиск в `product_code_mappings.mapped_code`.
        3.  Если в `product_code_mappings` найдено совпадение, взять из этой записи соответствующий `gtin`.
        4.  Использовать найденный `gtin` для всех дальнейших операций (печать, агрегация и т.д.), как это делается сейчас.
        5.  Если совпадение не найдено, предложить его создать выбрав из задания товар подходящий по смыслу.
    -   Такой подход не требует изменения сервисов, которые уже работают с `gtin`.

## 5. Преимущества нового подхода

-   **Минимальное вмешательство:** Не требуется изменять существующую таблицу `public.products` и основную логику приложения, работающую с ней.
-   **Обратная совместимость:** Система продолжает работать как раньше при сканировании российских GTIN.
-   **Простота реализации:** Изменения затрагивают только интерфейс администрирования и логику идентификации товара по коду.
-   **Решение задачи:** Позволяет однозначно определять товар по различным типам кодов (EAN, код производителя и др.).
