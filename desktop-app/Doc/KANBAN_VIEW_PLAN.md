# План разработки: Представление "Жизненный цикл заказа" (Kanban)

Этот документ описывает план разработки нового, независимого представления для визуализации полного жизненного цикла заказа в виде Kanban-доски.

## 1. Цели и задачи

- **Основная цель**: Создать единое визуальное пространство для отслеживания всех сущностей (уведомлений, заказов) на всех этапах их обработки, от создания уведомления до архивации заказа.
- **Наглядность**: Представить жизненный цикл в виде колонок (этапов), по которым перемещаются карточки (заказы/уведомления).
- **Независимость**: Новый функционал не должен изменять или нарушать работу существующих вкладок "Управление уведомлениями" и "Управление заказами". Он должен быть полностью самостоятельным.
- **"Только для чтения"**: На первом этапе Kanban-доска будет служить инструментом мониторинга. Перетаскивание карточек для изменения статуса не планируется, чтобы избежать случайных ошибок.
- **Быстрый доступ**: Клик по карточке должен открывать уже существующий детальный редактор для соответствующего уведомления или заказа.

## 2. Проектирование Kanban-доски

### 2.1. Этапы (колонки)

Доска будет состоять из колонок, представляющих ключевые статусы в системе.

1.  **Уведомления: Проект**
    - **Источник**: `ap_supply_notifications`
    - **Условие**: `status = 'Проект'`
    - **Описание**: Созданные, но не до конца оформленные уведомления.

2.  **Уведомления: Ожидание**
    - **Источник**: `ap_supply_notifications`
    - **Условие**: `status = 'Ожидание'`
    - **Описание**: Уведомления, готовые к созданию заказа.

3.  **Заказ создан**
    - **Источник**: `orders`
    - **Условие**: `status` не начинается с 'Архив' И `api_status` IS NULL.
    - **Описание**: Заказы, созданные из уведомлений, по которым еще не было действий с API.

4.  **Запрос кодов (ДМ.Код)**
    - **Источник**: `orders`
    - **Условие**: `api_status = 'Запрос создан'`
    - **Описание**: Ожидается подписание заказа в системе "Честный Знак".

5.  **Коды получены**
    - **Источник**: `orders`
    - **Условие**: `api_status = 'Коды скачаны'`
    - **Описание**: Коды загружены в локальную БД и готовы к дальнейшей обработке (печать, агрегация).

6.  **Агрегация (Внешнее ПО)**
    - **Источник**: `orders`
    - **Условие**: `status = 'delta'`
    - **Описание**: Данные выгружены для обработки во внешнем ПО (например, "Дельта").

7.  **Агрегация (Завершено)**
    - **Источник**: `orders`
    - **Условие**: `status = 'completed'`
    - **Описание**: Внутренняя агрегация кодов завершена (например, после загрузки из файлов).

8.  **Подготовка отчета**
    - **Источник**: `orders`
    - **Условие**: `api_status = 'Сведения подготовлены'`
    - **Описание**: Данные об использованных кодах отправлены в API, ожидается команда на формирование отчета.

9.  **Отчет отправлен**
    - **Источник**: `orders`
    - **Условие**: `api_status = 'Отчет подготовлен'`
    - **Описание**: Отчет о нанесении отправлен, ожидается проверка.

10. **Проверка отчета**
    - **Источник**: `orders`
    - **Условие**: `api_status = 'Отчет проверен'`
    - **Описание**: Отчет успешно принят и проверен. Заказ готов к архивации.

### 2.2. Содержимое карточки

Каждая карточка на доске должна содержать ключевую информацию:
- ID уведомления или заказа.
- Наименование клиента.
- Номер контейнера/ТС (из `orders.notes` или `ap_supply_notifications.vehicle_number`).
- Ключевые даты (планируемая дата прибытия, дата создания заказа).
- Количество позиций (уникальных GTIN).
- Общее количество кодов маркировки.
- Цветовая индикация, соответствующая текущему статусу.

## 3. План реализации

### Шаг 1: Бэкенд (Сервисный слой)

- Создать новый метод `get_kanban_data()` в `SupplyNotificationService` или в новом `KanbanService`.
- Этот метод будет выполнять два основных запроса:
  1. К `ap_supply_notifications` для получения данных по статусам 'Проект' и 'Ожидание'.
  2. К `orders` для получения данных по всем остальным статусам.
- Метод должен агрегировать и обрабатывать полученные данные, распределяя их по категориям (колонкам).
- Возвращаемый результат — словарь, где ключ — это название колонки, а значение — список словарей (карточек) для этой колонки.

### Шаг 2: Фронтенд (UI - `admin_ui_qt.py`)

- Добавить новый пункт меню "Kanban-доска" в `_build_ui`.
- Создать новый виджет `_build_kanban_page()`, который будет отвечать за отображение доски.
- Основной виджет страницы — горизонтальный `QScrollArea`, чтобы доска могла быть шире экрана.
- Внутри `QScrollArea` разместить `QWidget` с `QHBoxLayout`.
- Каждая колонка Kanban-доски будет представлять собой `QGroupBox` с `QVBoxLayout`. Внутри `QGroupBox` будет `QListWidget`.
- Каждая карточка в `QListWidget` будет кастомным виджетом (`KanbanCardWidget`), отображающим информацию из бэкенда.
- При открытии страницы будет вызываться `get_kanban_data()`, и полученные данные будут использоваться для заполнения `QListWidget` в каждой колонке.
- Реализовать `QTimer` для периодического автоматического обновления данных на доске (например, каждые 30 секунд).
- При двойном клике на карточку (`itemDoubleClicked` для `QListWidget`) определять ID сущности и открывать соответствующий редактор (`NotificationEditorDialog` или `OrderEditorFrameQt`).

### Шаг 3: Изоляция

- Вся логика UI будет инкапсулирована в новом методе `_build_kanban_page()` и его вспомогательных классах.
- Бэкенд-логика будет в новом методе `get_kanban_data()`, который не изменяет, а только читает данные.
- Существующие редакторы и диалоги будут переиспользоваться "как есть", без модификаций.

Это обеспечит полную независимость нового представления и минимизирует риски для существующей функциональности.
