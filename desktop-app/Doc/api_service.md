# Описание модуля `api_service.py`

`api_service.py` — это ключевой компонент архитектуры `desktop-app`, который выступает в роли централизованного шлюза для всех взаимодействий с внешним API "ДМ.Код". Его основная задача — инкапсулировать и упростить сложную логику HTTP-запросов, управления аутентификацией и обработки ошибок, предоставляя остальным частям приложения (в основном, UI) простой и понятный интерфейс.

## 1. Основные концепции и функциональность

### 1.1. Инкапсуляция

Сервис полностью скрывает детали реализации API-запросов. Вместо того чтобы в коде пользовательского интерфейса формировать URL, заголовки и тело запроса, UI-компоненты вызывают простые методы сервиса, такие как `api_service.get_participants()` или `api_service.create_order(payload)`. Это делает код UI чище и позволяет изменять логику API в одном месте, не затрагивая остальное приложение.

### 1.2. Автоматическое управление токенами

Взаимодействие с API требует использования временных токенов доступа (`access token`), которые периодически "протухают". `ApiService` полностью автоматизирует этот процесс:

1.  **Первичная аутентификация (`authenticate`)**: При первом запуске или при необходимости полной повторной аутентификации этот метод запрашивает у API пару токенов (`access` и `refresh`), используя логин и пароль из конфигурации.
2.  **Проверка и обновление (`_ensure_token`, `refresh_token`)**: Перед каждым запросом к API вызывается внутренний метод `_ensure_token`, который проверяет наличие `access_token`. Если токен отсутствует или просрочен (что определяется по ответу 401 от сервера), сервис автоматически пытается обновить его с помощью `refresh_token`.
3.  **Обертка для запросов (`_api_request`)**: Все запросы проходят через этот единый метод-обертку. Если запрос завершается с ошибкой 401 (Unauthorized), метод автоматически запускает процедуру обновления токена и **повторяет исходный запрос** один раз. Это делает процесс обновления токена полностью прозрачным для вызывающего кода.

### 1.3. Обработка полной повторной аутентификации

Иногда даже `refresh_token` может стать недействительным. В этом случае простого обновления недостаточно, и требуется полная повторная аутентификация с логином и паролем.

Для решения этой задачи `ApiService` использует механизм **обратного вызова (`callback`)**.

*   При инициализации сервис может принять функцию `reauth_handler`.
*   Если `refresh_token` не срабатывает, `ApiService` вызывает этот `reauth_handler`.
*   В приложении `desktop-app` эта функция (`_reauthenticate_api` в `admin_ui_qt.py`) может, например, показать пользователю диалоговое окно или выполнить аутентификацию в фоновом режиме.
*   Это позволяет отделить логику API от логики UI, который решает, как именно обрабатывать ситуацию, требующую вмешательства.

### 1.4. Высокоуровневые и низкоуровневые методы

Сервис предоставляет два типа методов:

*   **Низкоуровневые**: Это прямые обертки над конкретными эндпоинтами API (например, `create_order`, `get_printruns`, `download_printrun_json`). Они принимают `payload` и возвращают ответ сервера.
*   **Высокоуровневые (оркестраторы)**: Это методы, которые инкапсулируют целые бизнес-процессы, состоящие из нескольких последовательных вызовов API и пауз. Примеры:
    *   `request_codes_full_cycle`: Полный цикл запроса кодов, включая создание заказа, ожидание его активации и создание запроса на коды.
    *   `get_codes_full_cycle`: Полный цикл получения кодов, включая разбивку на тиражи, запрос JSON и скачивание.
    *   `prepare_utilisation_data_full_cycle`: Подготовка сведений об использовании кодов.

Эти методы принимают `progress_callback` — функцию, которую они вызывают для отправки логов о своем выполнении в пользовательский интерфейс в реальном времени.

## 2. Проверка статуса API в приложении

Для информирования пользователя о состоянии подключения к API в приложении реализован механизм фоновой проверки.

### 2.1. Визуальный индикатор

В правом нижнем углу главного окна (`AdminWindowQt`) находится небольшой круглый индикатор. Его цвет показывает текущий статус:
*   **Серый**: Статус неизвестен (проверка еще не выполнялась).
*   **Зеленый**: Последняя проверка прошла успешно, API доступно.
*   **Красный**: Последняя проверка не удалась, API недоступно или токен недействителен.

При двойном клике на индикатор запускается принудительная проверка.

### 2.2. Как это работает (механизм)

Проверка реализована в `admin_ui_qt.py` и состоит из нескольких частей:

1.  **Фоновый поток (`ApiStatusWorker`, `QThread`)**: Чтобы проверка не "замораживала" пользовательский интерфейс, она выполняется в отдельном фоновом потоке.
2.  **Периодичность (`QTimer`)**: Проверка запускается автоматически каждые 10 минут.
3.  **Метод проверки**: В качестве "пинга" используется вызов простого и быстрого метода `api_service.get_participants()`. Если этот вызов проходит успешно, значит, соединение есть и токен действителен.
4.  **Обновление UI**: После завершения проверки фоновый поток отправляет сигнал в основной поток UI, который обновляет цвет индикатора.

Такой подход обеспечивает актуальную информацию о состоянии API, не мешая работе пользователя.

## 3. Взаимодействие с другими сервисами

`ApiService` тесно интегрирован с другими частями приложения:

*   **`OrderService`**: `ApiService` использует `OrderService` для получения данных из локальной базы данных (например, чтобы сформировать `payload` для создания заказа в API) и для сохранения результатов, полученных от API (например, `api_order_id` или скачанные коды).
*   **`EmailService`**: После успешного завершения некоторых циклов (например, проверки отчета) `ApiService` может вызывать `EmailService` для отправки уведомлений.
*   **UI (`AdminWindowQt`, `ApiIntegrationFrameQt`)**: Пользовательский интерфейс является инициатором всех вызовов. Он создает экземпляр `ApiService`, передает ему `user_info` и `OrderService`, а затем вызывает его высокоуровневые или низкоуровневые методы в ответ на действия пользователя.

## 4. Реализация пошаговых сценариев в UI (`ApiIntegrationFrameQt`)

В то время как `ApiService` предоставляет высокоуровневые методы, которые выполняют всю бизнес-логику "под капотом", в пользовательском интерфейсе (`ApiIntegrationFrameQt`) реализованы аналогичные, но более интерактивные пошаговые сценарии. Эти методы-оркестраторы вызывают низкоуровневые функции `ApiService` и предоставляют пользователю детальный лог выполнения в реальном времени.

### 4.1. Ключевые отличия от `ApiService`

*   **Интерактивность**: Каждый шаг (например, "Создание заказа", "Ожидание активации", "Запрос кодов") сопровождается выводом сообщений в текстовое поле лога в UI.
*   **Управление потоками**: Чтобы длительные операции (особенно циклы ожидания с `time.sleep()`) не блокировали интерфейс, каждая такая функция запускается в отдельном фоновом потоке (`QThread`).
*   **Обновление UI**: Для обновления лога из фонового потока используется механизм сигналов и слотов Qt (`Signal` и `Slot`), что обеспечивает потокобезопасность.

### 4.2. Описание основных сценариев

*   **`_request_codes_flow` (Запросить коды)**:
    1.  **Проверка токена**: Выполняет простой вызов `get_participants()`, чтобы убедиться в валидности токена.
    2.  **Создание заказа**: Если у заказа в локальной БД нет `api_order_id`, формирует `payload` и вызывает `api_service.create_order()`. Сохраняет полученный ID.
    3.  **Ожидание активации**: В цикле с паузами вызывает `api_service.get_order_details()` до тех пор, пока статус заказа и всех его продуктов не станет `ACTIVE`.
    4.  **Создание запроса на коды**: Вызывает `api_service.create_suborder_request()`.
    5.  **Ожидание и сводка**: В цикле вызывает `api_service.get_suborders()`, пока не появится активный запрос на подпись. После этого выводит пользователю сводку по количеству кодов и GTIN.
    6.  **Обновление статуса**: Устанавливает локальный `api_status` заказа в 'Запрос создан'.

*   **`_get_codes_flow` (Получить коды)**:
    *   Этот метод последовательно запускает три других сценария: `_split_runs_task`, `_prepare_json_task` и `_download_codes_task`.

*   **`_prepare_report_data_task` (Подготовить сведения)**:
    1.  **Выгрузка данных**: В зависимости от статуса заказа (`delta` или `dmkod`), получает данные из локальной БД и порциями выгружает их в API через `api_service.upload_utilisation_data()`, сохраняя полученные `utilisation_upload_id`.
    2.  **Проверка итогов**: Собирает все `utilisation_upload_id` для заказа и в цикле запрашивает результаты обработки через `api_service.get_utilisation_result()`.
    3.  **Сводка и подтверждение**: Выводит пользователю сводную информацию по заказанным, полученным и успешно принятым кодам, после чего запрашивает подтверждение на создание отчета о нанесении.

*   **`_prepare_report_task` (Подготовить отчет)**:
    *   Получает из локальной БД все ID тиражей (`api_id`) для заказа и в цикле вызывает `api_service.create_utilisation_report()` для каждого из них.
