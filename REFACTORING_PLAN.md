# План рефакторинга desktop-app

## Анализ

Текущая архитектура `desktop-app` сильно завязана на файл `admin_ui_qt.py`, который представляет собой большой и сложный класс, отвечающий как за отображение, так и за бизнес-логику. Это затрудняет тестирование, поддержку и дальнейшее развитие приложения.

## Цели рефакторинга

*   **Разделение ответственности (Separation of Concerns):** Отделить UI от бизнес-логики.
*   **Повышение модульности:** Разбить большие классы на более мелкие и сфокусированные.
*   **Улучшение тестируемости:** Упростить написание юнит-тестов для бизнес-логики.
*   **Улучшение поддерживаемости:** Сделать код более понятным и легким для модификации.

## Пошаговый план

1.  **Создание слоя бизнес-логики (Business Logic Layer):**
    *   Создать новый модуль `desktop-app/src/logic/` (или `services/` если уже есть).
    *   Перенести всю бизнес-логику из `admin_ui_qt.py` в отдельные классы в этом модуле. Например, создать `OrderLogic`, `TaskLogic`, `ApiLogic` и т.д. Эти классы будут содержать методы для работы с данными, вызовов API, и т.д. `admin_ui_qt.py` должен только вызывать методы этих классов.

2.  **Рефакторинг `admin_ui_qt.py`:**
    *   Разбить класс `AdminWindowQt` на более мелкие виджеты. Каждый виджет будет отвечать за свою часть UI (например, `OrdersWidget`, `TasksWidget`, `CatalogsWidget`).
    *   Каждый виджет должен взаимодействовать только со слоем бизнес-логики, а не напрямую с базой данных или API.
    *   Убрать всю бизнес-логику из `AdminWindowQt`. Оставить только код, отвечающий за отображение и взаимодействие с пользователем.

3.  **Внедрение модели MVC/MVP/MVVM:**
    *   Рассмотреть возможность внедрения одного из архитектурных паттернов (MVC, MVP, или MVVM) для более четкого разделения кода.
    *   **Model:** Слой доступа к данным (уже частично реализован в `db_connector.py` и сервисах).
    *   **View:** UI-компоненты (виджеты).
    *   **Controller/Presenter/ViewModel:** Слой бизнес-логики.

4.  **Рефакторинг сервисов:**
    *   Проанализировать существующие сервисы (`ApiService`, `OrderService`, и т.д.) и убедиться, что они не содержат UI-зависимого кода.
    *   Если сервисы содержат UI-код, вынести его в соответствующие виджеты.

5.  **Написание тестов:**
    *   Написать юнит-тесты для классов бизнес-логики.

## Ожидаемый результат

*   Более чистая и понятная архитектура приложения.
*   Упрощение добавления нового функционала.
*   Возможность независимого тестирования бизнес-логики и UI.
*   Снижение связанности компонентов системы.
