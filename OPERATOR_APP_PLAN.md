# План разработки и запуска приложения Оператора

Этот документ описывает пошаговый план по созданию надежного механизма запуска и авторизации для приложения Оператора (`run_oper.py`), основанный на лучших практиках из основного приложения Администратора (`run.py`, `src/auth_qt.py`).

## 1. Анализ существующей системы (Приложение Администратора)

Основное приложение использует сложную, но надежную схему запуска:

1.  **`run.py` (Точка входа):**
    *   Настраивает системные пути для поиска DLL, что критически важно для скомпилированных `.exe` файлов (`cx_Freeze`, `PyInstaller`).
    *   Производит принудительные импорты библиотек, которые могут быть пропущены сборщиком.
    *   Централизованно настраивает систему логирования, читая конфигурацию из `.env` файла.
    *   Передает управление модулю авторизации `src.auth_qt.py`.

2.  **`src/auth_qt.py` (Модуль авторизации):**
    *   Отображает окно входа (логин/пароль).
    *   Поддерживает два режима авторизации:
        *   **Локальный:** При наличии `config.ini` - подключается напрямую к БД клиента.
        *   **Онлайн:** При отсутствии `config.ini` - подключается к центральной БД, получает данные пользователя и конфигурацию для подключения к его клиентской БД.
    *   По итогам авторизации формирует ключевой объект `user_info`, содержащий всю необходимую информацию для работы сервисов (конфигурации БД, API, данные пользователя).
    *   В зависимости от роли пользователя в `user_info`, запускает соответствующее главное окно (`AdminWindowQt` или `SupervisorWindowQt`).

## 2. Требования к приложению Оператора

Приложение Оператора имеет более простые и четкие требования:

*   **Авторизация:** Происходит не по логину/паролю, а по сканированию кода-пропуска. Эта проверка выполняется в базе данных клиента.
*   **Источник конфигурации:** Все настройки для подключения к БД должны браться исключительно из `.env` файла.
*   **Подключение к БД:** Необходимо поддерживать два сценария подключения к клиентской БД:
    1.  **Локальная сеть:** Без SSL-шифрования.
    2.  **Публичная сеть:** С использованием SSL-сертификата.
*   **Отсутствие API:** Приложению не требуется взаимодействие с внешним API "Честного знака".

## 3. Пошаговый план реализации `run_oper.py`

### Шаг 1: Подготовка окружения и конфигурации (`setup_environment`)

Создать функцию `setup_environment()`, которая будет выполнять следующие действия:

1.  **Настройка путей:** Полностью скопировать логику из `run.py` для настройки путей поиска DLL. Это обеспечит работоспособность как в IDE, так и в `.exe`.
2.  **Чтение `.env`:** Загрузить переменные окружения из файла `.env`.
3.  **Формирование `user_info`:**
    *   Прочитать все необходимые переменные для подключения к БД из `os.getenv()` (например, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `LOCAL_SERVER_ADDRESS`, `LOCAL_SERVER_PORT`).
    *   Создать словарь `user_info`, структура которого будет совместима с той, что ожидают сервисы и `db_connector`.
    ```python
    user_info = {
        "name": "OperatorMode",
        "role": "оператор",
        "client_db_config": {
            'id': 0, # Признак локального режима
            'db_host': os.getenv("DB_HOST"),
            'db_port': os.getenv("DB_PORT"),
            # ... и другие параметры
        }
    }
    ```
4.  **Проверка соединения:** После формирования `user_info`, немедленно выполнить тестовое подключение к БД. Использовать `get_client_db_connection(user_info)`. Если подключение не удалось, приложение должно вывести критическую ошибку и завершиться. Это предотвратит запуск UI без доступа к базе.

### Шаг 2: Настройка логирования (`setup_logging`)

Создать функцию `setup_logging()`, которая:

1.  Копирует логику из `run.py` для инициализации `logging`.
2.  Настраивает запись логов в отдельный файл, например, `app_oper.log`, чтобы не смешивать их с логами основного приложения.

### Шаг 3: Принудительные импорты

В самом начале файла `run_oper.py` добавить блок `try...except ImportError` для явного импорта библиотек, которые могут понадобиться `cx_Freeze`. Например: `PySide6`, `sqlalchemy`, `greenlet`.

### Шаг 4: Основная логика запуска (`main`)

Создать главную функцию `main(user_info)`, которая будет принимать `user_info` как аргумент.

1.  **Инициализация QApplication:** `app = QApplication(sys.argv)`.
2.  **Инициализация сервисов:**
    *   Создать `TaskService`, передав ему `user_info`.
    *   Создать `CatalogsService`. Ему требуется `user_info` и функция для подключения к БД.
    ```python
    from src.db_connector import get_client_db_connection
    db_conn_func = lambda: get_client_db_connection(user_info)
    catalogs_service = CatalogsService(user_info, db_conn_func)
    ```
    *   **Важно:** `ApiService` не создается и не используется.
3.  **Запуск UI:**
    *   Создать экземпляр `OperatorLoginWindow`, передав ему `task_service`.
    *   Вызвать `login_dialog.exec()`. Этот метод отобразит окно как модальное и приостановит выполнение кода до закрытия окна.
    *   Проверить результат `exec()`:
        *   Если диалог был успешно "принят" (т.е., авторизация пройдена), получить `task_info` из `login_dialog`.
        *   Создать экземпляр `OperatorWorkWindow`, передав ему все необходимые сервисы и `task_info`.
        *   Показать `OperatorWorkWindow` и запустить главный цикл приложения `sys.exit(app.exec())`.
        *   Если авторизация была отменена, просто завершить приложение `sys.exit(0)`.

### Шаг 5: Точка входа (`if __name__ == "__main__"`)

Обернуть весь процесс запуска в блок `if __name__ == "__main__"`, который будет:

1.  Вызывать `setup_environment()` для получения `user_info`.
2.  Вызывать `setup_logging()`.
3.  Вызывать `main(user_info)`.
4.  Обернуть все вызовы в `try...except`, чтобы перехватывать и логировать любые критические ошибки при старте.

Этот план позволит создать для приложения оператора такой же надежный и предсказуемый механизм запуска, как и у основного приложения, но адаптированный под его специфические требования.
